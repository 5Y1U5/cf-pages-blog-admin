# 統合の判断メモ

このパッケージは、同じ機能を持ちながら別々に育ってしまった複数の実装（以下 A〜D）を
1本にまとめたもの。ファイルごとに「どれを正とするか」を選ぶ必要があり、
その判断と理由をここに残す。コードには理由を書かない（読む人が増えるほど古くなるため）。

---

## 1. 実装が割れていた箇所と、採用したもの

### 1-1. 記事の公開（`server/handlers/posts/publish.ts`）

| 論点 | 割れ方 | 採用 |
|---|---|---|
| 公開の必須項目 | A/B/D はタイトルと本文だけ。C はさらに slug・日付・カテゴリも必須 | **タイトルと本文だけ。** ただし `publish.requiredFields` として設定可能にした |
| 未入力項目の扱い | A/B/D は公開時に自動補完（カテゴリ・日付・要約・アイキャッチ・著者）。C は補完なし | **自動補完する** |
| 公開日の基準 | B のみ +9 時間。他は UTC | **設定 `publish.timezoneOffsetMinutes` で指定（既定 540）** |
| 未来日での公開 | B のみ拒否。他は許可 | **既定で拒否（`publish.blockFutureDate`）** |

必須項目を緩める判断の根拠: slug は保存時に自動生成され、日付は当日が既定で入り、
カテゴリも既定値が自動選択されるため、画面上はまず空にならない。
条件を厳しくしても弾かれるケースがほとんど無く、弾かれたときのメッセージが分かりにくいだけだった。
設定項目として残したのは、将来「日付だけは必ず人が確認する」といった運用を選べるようにするため。

未来日を拒否する判断の根拠: 静的サイトを定期再ビルドしていない構成では、未来日で公開すると
公開側の `date <= today` フィルタで除外され、次の再ビルドまで
「公開は成功したのにページが出ない」状態になる。エラーで止めたほうが誤解が少ない。
再ビルドを定期実行している導入先では `blockFutureDate: false` にできる。

### 1-2. 記事の新規作成（`server/handlers/posts/index.ts`）

| 論点 | 割れ方 | 採用 |
|---|---|---|
| slug の衝突 | B のみ `-2` `-3` と連番を付けてユニーク化。他は一意制約違反で 500 | **連番を付ける方（B）** |
| 新規作成時に保存する項目 | B は更新と同じ全項目。他は一部を落としていた | **全項目（B）** |

同じタイトルで2本目を作った瞬間に 500 になる挙動は、原因が利用者から分からない。

### 1-3. カテゴリの作成（`server/handlers/categories/index.ts`）

`code` の重複を事前に検出して日本語で返す実装（B）を採用した。
`ON CONFLICT` は `slug` しか拾えないため、`code` が衝突すると一意制約違反で 500 になる。

### 1-4. ユーザーの更新・削除（`server/handlers/users/detail.ts`）

B にしか存在しなかった。無効化・ロール変更・パスワード再発行・削除に加えて、
**最後の有効な管理者を降格・無効化・削除できない**ガードを持つ。全体へ配る。

### 1-5. 画像アップロードの事前検査（`ui/lib/admin-image.ts`）

3系統に分かれていた。

| 系統 | 形 | 判定結果の返し方 |
|---|---|---|
| A | `isUploadableImage()` ＋ `unsupportedImageMessage()` | 呼び出し側が2つの関数を順に呼ぶ |
| B | `describeUnsupportedImage()` | 呼び出し側が文字列の有無を見る |
| C | `PreparedImage.blockedReason` | 前処理の戻り値に理由が入る |

**C（`blockedReason` 方式）を採用した。** 理由:

- 前処理（縮小・再エンコード）の結果と「送ってよいか」の判定が1つの値にまとまる。
  A の形は、前処理のあとに別の関数で判定し直す必要があり、
  **前処理で形式が変わった場合の再判定を呼び出し側が忘れられる**
- C だけが「変換後のファイルをもう一度判定する」処理を持っていた。
  変換に失敗して元の形式のまま返ったケースを取りこぼさない
- サーバー側が拒否する拡張子リストと許可 MIME の複製が C だけ明示的にコメントされており、
  サーバーの実装を変えたときに直す場所が分かる

あわせて、サーバーが英語で返すアップロードエラーの日本語対訳表も同じモジュールに移した
（元は画面コンポーネント側に置かれていて、`admin-image.ts` だけ移植しても文言が英語のまま残る）。

### 1-6. 記事の削除権限

削除は物理削除で復元手段がないため、既定は管理者のみ。
ただし `permissions.deletePost` として設定可能にした（緩めたい導入先が出たときのため）。
画面側の削除ボタンも同じ設定を見るので、設定を変えれば API と画面の両方が追従する。

## 2. 設計書からあえて変えたところ

### 2-1. `BlogAdminEnv` の置き場所

設計上は設定モジュールが `BlogAdminEnv` も export する想定だったが、
**`config/env` に分けた。**

`BlogAdminEnv` は `D1Database` / `R2Bucket` を参照する。これらは
`@cloudflare/workers-types` のグローバル宣言で、TypeScript は d.ts に
`/// <reference types="@cloudflare/workers-types" />` を書き出す。
その d.ts を管理画面 UI 側から import すると、**導入先のアプリ側のビルドに
Workers の型が流れ込み、DOM の型と衝突する**（`Response` などが二重宣言になる）。

分けたことで、`./config` は Cloudflare の型を一切参照しない純粋な型定義になり、
UI からもサーバーからも安全に import できる。

### 2-2. ハンドラは（1つを除いて）すべてファクトリにした

設計上は「設定不要のものが16ファイル中7ファイル」とあったが、
セッション Cookie 名を設定へ出した時点で、**セッションを読むハンドラはすべて設定が要る**。
実際に設定不要なのは R2 の配信ハンドラだけなので、そこだけ素の
`onRequestGet` を export し、残りはすべて `createXxxHandlers(config)` に揃えた。
形が揃っているほうが `init` の生成も導入時の確認も楽になる。

### 2-3. 記事一覧のヘッダーに拡張用の口を足した

共通化の対象外にした機能（自動化画面など）へのリンクを持つ導入先があるため、
`AdminPostsClient` に `headerActions` を足した。管理者にだけ描画される。
パッケージ側にその機能を持ち込まずに、リンクだけ置けるようにするための最小限の口。

### 2-4. ロールの識別子は変えず、表示名だけ中立にした

`client_publisher` という識別子は D1 の CHECK 制約・TypeScript の型・全ルートのガードに
埋め込まれていて、改名するには稼働中のデータベースの移行が要る。**識別子は据え置く。**
画面に出るラベルだけを中立な日本語（「編集・公開」「管理者」「閲覧のみ」）にした。

## 3. セキュリティまわりで手を入れた／入れなかったもの

| 項目 | 判断 |
|---|---|
| 初期パスワード生成の剰余バイアス | **直した。** 文字数で割り切れない範囲のバイトを捨てる（棄却サンプリング）。文字集合と長さは変えていない |
| ログイン試行制限が記録テーブル未作成のとき素通りする | **挙動は維持。** 可用性を優先する判断は妥当だが、素通りに気づけるよう警告ログを出すようにした |
| PBKDF2 の反復回数 | **据え置き（100,000）。** ハッシュ文字列に反復回数を埋め込む形式なので引き上げても既存ログインは壊れないが、Workers ランタイム側に上限があるため、実環境で確認せずに上げない |
| IP 単位のログイン試行制限 | 既に入っていたものをそのまま採用（メール単位に加えて、同一 IP からの失敗も数える） |
| アップロード検査の仕様がクライアント側に複製されている | **対応不要。** サーバーは Content-Type を信用せず先頭バイトで実体を判定するため、複製された規則から検査を回避する経路は無い |

## 4. 公開前チェックスクリプトについて

検査パターンに「検出したい語」をそのまま書くと、**スクリプト自身が必ず引っかかる**。
そのため

- 一般的な語は Unicode エスケープで書く（`scripts/check-public-safe.mjs`）
- 導入先固有の語はリポジトリに置かず、`PUBLIC_SAFE_EXTRA_PATTERN` で外から渡す

という形にした。公開リポジトリに導入先の名称一覧を置いてしまうと、
それ自体が守ろうとしていた情報の公開になる。
